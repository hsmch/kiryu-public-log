## 1. 経緯と問い

### 構造整理の途中で行き当たった問題

2026年9月24日、公開サイトが「機能は揃ったが情報が煩雑で見にくい」状態にあることから構造整理を始めた。棚卸しの結果、原因は情報量ではなく階層の欠如（ナビ9項目の並列、トップ10セクション、装飾）であると判断し、ナビとトップを「議会 / 議員 / テーマ / まちの数字 / 使い方」の5分類に絞る実装を行った。

その過程で「テーマ」だけが他と性質が違うことが分かった。テーマ（AIタグ）の対象は議案と一般質問だけで、議会の記録を分野という別の軸で引いた索引にすぎない。つまり議会・議員・まちの数字が「データの出どころ」で切った分類であるのに対し、テーマは「運営の中身」で切った分類であり、同じ列に並ばない。

ここから、より根本的な問いが出てきた。

> **市の運営は、市民からどうすれば見えるのか。KPL はその中のどこを見せているのか。**

サイトの中の並べ替えでは、何を見せるべきかは見えてこない。サイトから一段引いて、市の運営がどこでどう公開されているかを地図にする必要がある。

### 3月のレポートとの関係

3月のレポートは「中立アーカイブか参加促進か」「どの層をターゲットにするか」「気づきと行動の仕組み」を扱った。本レポートはその手前にある「そもそも何が運営の情報なのか」を扱う。3月の結論（中立堅持、単一サイト、関心中の市民が最重要）は本レポートでは前提として扱わず、範囲を決めた後に再検討する。

## 3. 市の運営はどう動き、どこで公開されるか

### 二元代表制の構造

市の運営は、市長を長とする**執行機関**が担う。計画を立て、予算案・条例案・契約議案を作り、議会の議決を経て、入札・契約・事業執行を行い、決算・監査・評価を受けて次の計画に戻る。**市議会**はこの流れの中で議決と監視を担い、一般質問で執行部に問い、請願・陳情を審査する。**監査委員**や事案ごとの**第三者委員会**が点検を担い、市民は選挙・傍聴・パブリックコメント・請願・情報公開請求で関わる。

```
  計画 ──▶ 予算案・条例案・契約議案 ──▶ ┌────────────┐ ──▶ 執行 ──▶ 決算・監査・評価 ──┐
   ▲        （執行機関: 市長・部局）    │   市議会    │   （入札・契約・事業）         │
   │                                    │ 審議・議決  │                                │
   │                                    │ 一般質問    │                                │
   │                                    │ 請願・陳情  │                                │
   │                                    └────────────┘                                │
   └───────────────────────────────────────────────────────────────────────────────────┘
        市民の関与: 選挙 ／ 傍聴 ／ パブリックコメント ／ 請願 ／ 情報公開請求
```

### KPL が見ている場所

KPL のデータソースは市議会サイト・財政ページ・統計ページの3系統で、図の中では「市議会」の箱の中身（議案・採決・投票個票・一般質問・議事録）と、その箱に入る前の「予算案」、結果側の「人口」だけを見ている。

重要なのは、**議会は運営そのものではなく、運営が通過する検問所**だという点である。議案の大半は市長提出で、予算・条例・大型契約が議会を通るときに初めて可視化される。一般質問は議員が執行部に問う場である。KPL が持つ「議会の記録」は、行政の決定のうち議会を通った部分を、議会の手続き（定例会・議案番号）の順に並べたものだと言える。

## 5. 地図から見えること

### 5.1 空白は「実行」と「計画」

KPL は「決める」の層に深く集中し、「実行する」「実行を点検する」「計画する」がほぼ空白である。

3月のレポートに書かれた動機は、生活保護の支給運用と新庁舎建設の入札妨害だった。どちらも**執行側**の問題である。市はこの事件について第三者委員会の資料、市長メッセージ、新庁舎関連の各契約締結ページを公開しているが、今の KPL ではそれらは一般質問の題名として通過したときにしか現れない。動機と現状のギャップは、3月に指摘された「文脈と解説の薄さ」ではなく、そもそも執行側を見ていないことにある。

### 5.2 分類の軸が混在していた

9月の構造整理で「テーマ」が浮いたのは、軸の混在が原因である。

| 軸 | 分類の例 | 性質 |
|---|---|---|
| データの出どころ | 議会 / 議員 / 財政 / 統計 | 取得したデータの単位で並ぶ |
| 運営の要素 | 決める / お金 / 実行 / 人 / 関わる | 市の運営の働きの単位で並ぶ |
| 議会データの見方 | 定例会ごと / 分野別 / 議員別 / 議員間比較 | 同じデータの別の切り口 |

現在のナビは1行目の軸で、テーマは3行目、3月の「問いかけ型ナビゲーション」（税金は何に使われている？ など）は2行目の軸に近かった。

ただし、**現在のデータ範囲では1行目と2行目の軸は1対1に対応する**（議会＝決める、議員＝人、まちの数字＝お金と成果、使い方＝関わる）。2つの軸が分かれるのは、執行側のデータ（実行・点検・計画）を加えたときであり、それまでは分類の語彙の問題にとどまる。範囲を決めれば、どの軸で切るかも決まる。

### 5.3 「議会を通る情報」は自動化しやすく、執行側は半手動になりやすい

議会サイトは定例会ごとに規則的な URL とテーブルで公開され、スクレイプが安定する。一方、入札結果は HTML だが随時更新、決算・監査・計画は PDF で年数回。範囲を執行側に広げるほど、3月のレポートが個人運営の制約として挙げた「何をやらないか」の判断が重くなる。ただし決算・監査は年数回なので、半手動でも回る。

### 5.4 名前と範囲の一致

"Kiryu Public Log" という名前と「市政・議会の公開情報」という説明文は、市の運営全体を想起させる。議会に徹するなら「議会の記録」であることをサイト名の説明・About・トップの1行で明示すべきであり、運営全体を名乗るなら少なくともお金の結果（決算）と実行（入札・監査）を扱う必要がある。名前が約束する範囲と、実際の範囲を一致させることが、構造整理より先にある。

## 6. 範囲の選択肢と情報設計への影響

### 3つの選択肢

| | A. 議会ログに徹する | B. 市の運営全体を見るサイトへ | C. 段階的: 議会ログ ＋ お金の流れ |
|---|---|---|---|
| **範囲** | 決める ＋ 議員 ＋ 予算 ＋ 人口 | 地図の全行 | A ＋ 決算 ＋ 入札・契約 ＋ 監査 |
| **追加で取るデータ** | なし（議事録の表示は範囲内） | 計画・入札・監査・記者会見・パブコメ・組織 | 決算（PDF、年1）、入札結果（HTML、随時）、監査結果（PDF、年数回） |
| **自動化** | 現状どおり全自動 | 大半が PDF・随時更新で半手動 | 入札は自動化の余地あり。決算・監査は年数回なので半手動でも可 |
| **動機との整合** | 入札妨害・生活保護運用は追えない | 追える | 入札はお金の流れとして追える。生活保護運用は監査・一般質問経由 |
| **中立性リスク** | 低 | 監査・第三者委員会の扱いで「評価」に踏み込みやすい | 低〜中。数値と原文リンクに徹すれば低 |
| **工数** | 小 | 大。個人運営の持続性に影響 | 中。データ種別ごとに1本ずつ |
| **ナビの軸** | データの出どころ: 議会 / 議員 / まちの数字 / 使い方 | 運営の要素: 決める / お金 / 実行 / 人 / 関わる | 運営の要素寄り: 議会 / 議員 / お金 / 使い方 |
| **テーマの置き場** | 議会の下（分野別） | 横断索引として各要素の下 | 議会の下（分野別） |
| **名前・説明** | 「桐生市議会の記録」と明示 | 「市の運営を見る」と言い切る | 「議会と市のお金の記録」 |

### 情報設計への影響

どの案でも共通:

- URL は変えない。9月24日の装飾撤去とトップ簡素化はそのまま有効
- テーマは横並びの分類ではなく、議会の記録を分野で引く見方として議会の下に置く
- 投票分析も同様に議会と議員の下

案によって変わるのはナビの語彙と、トップの各カードが何を代表するかである。A なら「議会 / 議員 / まちの数字 / 使い方」の4枚、C なら「まちの数字」が「お金」に広がり人口はその中か独立か。B なら運営の要素で切り直す。

### 決定: B を目標にする（2026年9月24日）

運営者の意向は B（市の運営全体を見るサイト）である。本レポートが B を「持続しにくい」としたのは地図の全行を一度に構造化する前提であり、次の3条件で段階的に進めれば個人運営でも成立する。

1. **枠を先に作り、中身は後から**: KPL の方針は当初から「公式情報への入口」なので、未構造化の要素は公式ページへの整理された入口として先に置く。空の部屋ではなく、入口のある部屋になる
2. **データは自動化しやすい順に1本ずつ**: 入札結果・パブコメ募集（HTML）を日次収集に乗せ、決算・監査・計画（PDF、年数回）は pdf-parse と Claude API で半手動にする
3. **範囲を名乗り、構造化の程度を正直に示す**: 「市の運営を見る」と言い切り、各分類で何が構造化済みで何が入口だけかをサイト上に明示する

### 今回の構造整理との関係

9月24日の構造整理は、この決定に合わせてナビとトップを運営の要素の軸で切り直した。既存の URL は変えず、`/operations`（実行）を1ページ追加した。入口リンクは `data/entry-points.json` で手動管理し、各分類の着地ページ末尾に「公式サイトで見る」として表示する。

| 分類（ラベルは暫定） | 運営の要素 | 着地ページ | 構造化済み | 入口のみ（公式リンク） | 次に足すデータ |
|---|---|---|---|---|---|
| 決める | 決める、ルールを作る | `/sessions` | 定例会・議案・投票個票・一般質問（議事録は取得済み） | 議会公式・会議録検索・例規集・教育委員会会議録 | 議事録の表示 |
| お金 | お金の計画・結果、成果（人口） | `/finance` | 予算内訳・経年・基金・財政指標・人口 | 予算・決算・主な財政指標 | 決算 |
| 実行 | 実行、点検、計画、執行部の発信 | `/operations` | なし | 入札情報・新本庁舎整備・監査結果・第三者委員会・計画・市長公約・記者会見 | 入札結果（自動）、監査・計画（半手動） |
